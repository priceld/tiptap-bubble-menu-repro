Tiptap menus: a destroyed view still runs its deferred work

BubbleMenuView and FloatingMenuView defer some of their work with setTimeout, and destroy() never stops it. ProseMirror destroys every plugin view whenever the plugin list changes, so a registerPlugin call while that work is pending leaves a destroyed view acting on the menu.

Each menu below moves focus into its input as it opens. When a destroyed view acts on the menu, it moves the menu element, and that drops the input's focus.

A bubble menu for editing a link's text. It opens when the selection is in the link.

Deferred work to test

Steps

  1. Click Reset. This puts the caret inside the link without focusing the editor, so focus stays on the button.
  2. Press Tab to move focus into the editor.
  1. Click Reset. This puts the caret at the start of the editor and focuses it.
  2. Double-click the word docs in the link.

Expected: the menu opens with the link text selected in its input, ready to type over.
Actual: the menu opens, but focus ends up on <body>. Typing goes nowhere.

Clear it and repeat the steps, and the input keeps focus.
